### FINDING 1 (routed to plan 06.1-06) — the recovery bar at lags needs a CONVERGED fit, and the door's budget does not give one

This is the substantive result of Task 1 and it is recorded in the contract's `preconditions:`
rather than worked around. Worst relative error per column, learning rate selected by train loss
in every cell, four seeds:

| points | epochs | seed 42 | seed 43 | seed 7 | seed 11 |
|---|---|---|---|---|---|
| 1200 | 110 (`np::door_epochs`) | 0.0915 | **0.2293** | **0.4660** | **0.3326** |
| 1200 | 320 (the AR cap) | 0.0528 | 0.0659 | 0.0668 | 0.0667 |
| 2400 | 90 (`np::door_epochs`) | **0.2191** | **0.3597** | **0.3897** | **0.2954** |
| 2400 | 320 (the AR cap) | 0.0677 | 0.0628 | **0.1663** | 0.0901 |

**The mechanism is visible in every failing row and is exactly the one D-30 predicted.** The
FIRST column of each event — whose seven-day lag window contains no earlier day of the same
window — recovers correctly at every budget (7.7 to 8.7 against a planted 8.0). The TRAILING
columns, whose lag windows overlap the event, drift anywhere from 4.3 to 10.7, one run producing
a **negative** weight of −1.108. The AR term can read the effect out of the lags, so the split
between the two terms is under-determined rather than wrong, and it is the trailing columns that
pay for it.

So `equations.event_effect_recovery_rel` is **not** a claim that the shipped door configuration
recovers the effect at lags. Plan 06.1-06 opens the arm and therefore chooses the budget the
door configures; it owns closing this. Nothing reaches a caller meanwhile — the arm is refused.

**A harness artifact was found and corrected inside this finding**, which is why the 2400-point
rows are trustworthy: a fixed 2018–2021 occurrence list left the second half of a 2400-day series
event-free, and `np::sample_weight` weights that half MORE (`newer_w` = 2). Re-measured with the
occurrence list spanning the series, the 2400-point lag-free worst error moved from 0.034–0.038
to 0.017–0.025. The generator is now span-aware and the reason is in its doc comment.

## Task 2 — the C-08 event-column term

### The shape, pinned rather than described

```
request_train_cost = n_lrs * epochs * n_samples * ( (n_lags + 1) + fit_np_event_cost_per_column * E )
```

`(n_lags + 1)` is the per-sample feature width the optimiser sweeps; the block adds work to that
width, and the measured growth is a per-step slope, so the added work is paid once per sample per
epoch. The contract's `formula:` carries that string verbatim and the verify regex requires the
event term inside the same parentheses as `(n_lags + 1)`.

### The calibration — `just forecast-np-event-calibration`, release, aarch64

Host **Mac16,7 Apple M4 Pro, Darwin 25.6.0**; arch **aarch64**; date **2026-09-21**; commit
**610f5301a**; 1200 contiguous daily points, `n_lags_cal = 0`, 30 epochs, seed 42.

| E | 0 | 7 | 28 | 84 | 210 | 504 | 1000 |
|---|---|---|---|---|---|---|---|
| µs/step | 13.327 | 15.841 | 19.068 | 21.574 | 33.170 | 57.468 | 105.446 |

Least squares over the seven points: **intercept a = 14.4605 µs/step**, **slope b = 0.089836
µs/column**, **r² = 0.998067**. This reproduces spike 013's `12.9 + 0.085·E` on a different box.

The coefficient is `b·(n_lags_cal + 1)/a`, which reduces to `b/a` **only because this calibration
is lag-free** — `n_lags_cal` is a contract key so the reduction is checkable rather than assumed.
It is a **ratio**, so the batch size divides `a` and `b` identically and cancels; that is why it
is never an absolute µs figure, which the door could not convert at check time.

**Three runs at the same commit** (CLAUDE.md rule 6 — one input is an anecdote) fitted raw
coefficients **0.006213 / 0.005815 / 0.005723**, an 8.6 % spread. The **largest** is the basis:
rounded UP to the next 1e-4 → 0.0063, × safety factor 2 → **`fit_np_event_cost_per_column =
0.0126`**. The safety factor covers an unknown-direction host difference against the runner D-32
names, and it is stated with its reason rather than folded silently into the value, so the
on-target measurement can replace the number and the factor independently.

`np_event_calibration` re-asserts `shipped >= freshly fitted` on every run, so the sweep is itself
a live one-sided guard against under-pricing on any host it is run on.

### The closure — OBSERVED, as a ratio

```
measured(E)/measured(0)  <=  priced(E)/priced(0)
      7.9122x            <=       14.0000x          headroom 6.0878
     (105.446 / 13.327 µs/step)   (5 544 000 / 396 000)
```

Both measured numbers are READ from the C-08 `calibration:` mapping through
`test_support::contract_value`, never from a literal. Both ratios are dimensionless and taken at
the same geometry, so batch, steps and samples cancel out of both sides. One-sided: over-pricing
is safe, under-pricing is the defect.

### The shape discriminator — two geometries

| n_lags | 1200 points (1200 samples, 110 epochs) | 12 000 points (12 000 samples, 50 epochs) |
|---|---|---|
| 0 | **14.000000** | **14.000000** |
| 7 | **2.625000** | **2.625000** |

Identical across a 10x change in samples AND a change in the epoch budget — which is true of the
width form and false of `product + c*E`.

### OBSERVED RED under the rejected shape

Mutating `train_cost` to `product + c*E` turns **all three** SC4 guards red, each naming the real
cause rather than a symptom:

```
the_event_column_underpricing_is_observed_closed:
  UNDER-PRICED at 1000 event columns: the measured work grows 7.9122x
  while the price grows only 1.0001x.

the_event_cost_shape_scales_with_geometry:
  priced ratio 1.0000985 at 1200 points and 1.0000217 at 12000 points.
  The event term is therefore NOT inside the per-sample width.

the_event_width_is_rounded_up_and_monotone: also red.
```

The mutation was reverted; HEAD carries the width form.

### The enumeration decision, implemented as decided

`every_cost_ceiling_constant_is_named_by_an_axis` was **left alone** — its filter is correct,
and widening it would make it assert that a coefficient is a bound and force inventing an axis
whose `bound:` no door check compares against. Its vacuity guard count is **unchanged at 15**
(`fit_np_event_cost_per_column` does not start with `fit_max_`).

The sibling `every_cost_coefficient_constant_is_named_by_an_axis_formula` derives its list from
`constants:` keys containing `_cost_per_`, asserts each appears verbatim in some axis `formula:`,
and carries its own vacuity guard. The **general form** — every constant in exactly one named
category, each with its own obligation — is recorded as a named follow-up in the contract beside
the constant and in the test's rustdoc, and is explicitly **not** claimed closed.

### The in-suite wall budget — measured, not assumed

`sc1_wall_sweep` runs 19 compositions in **6.956 s** against its 120 s CI budget (7.19 s at the
06-16 baseline). The event axis added nothing to it, because the calibration sweep is `#[ignore]`d
and reachable only through the `just` recipe — the fallback the plan named. The existing test was
**not** `#[ignore]`d to make room.

### 2. [Rule 1 — verify defect] `t1d`'s `request_train_cost` regex is truncated by a nested parenthesis

`request_train_cost\([^)]*\)` stops at the first `)`, so a call whose earlier argument contains
parentheses is truncated. Measured: `crate::np::request_train_cost(&d, days.len(), n_lags)` was
reported as `request_train_cost(&d, days.len()`, which would have FAILED the `, 0` check even
with a correct implementation. Fixed by binding `let n_points = days.len();` at that call site
(a clearer call site either way), but **the regex remains fragile** — any future call site with a
nested paren before the event count will be mis-read. Flagged for plan 06.1-06, which edits these
same call sites.

### 3. [Rule 1 — acceptance criterion contradicts its own task] "`forecast.rs` is unchanged by this task"

Task 1's acceptance-criteria list still carries the pre-review line
`crates/aprender-forecast/src/forecast.rs is unchanged by this task`, which its own `<action>`
section explicitly replaces ("The earlier draft said 'do not touch `forecast.rs`' and
simultaneously required new fields on `TrainConfig` … That is not satisfiable"), and which the
Review Dispositions Ledger records as fixed at HIGH severity. The action text and the behavioural
verify were followed; the stale criterion was not. The door's exhaustive `TrainConfig` literal and
its three predict call sites **must** change for the crate to compile.

### 4. [Rule 3 — blocking, mechanical] `examples/mase_rolling_origin.rs` had to be updated

Not in `files_modified`. It builds an exhaustive `np::TrainConfig` literal and calls
`np::predict_ts`, so the crate does not compile under `--all-targets` (which the clippy gate uses)
without the same mechanical update the door got. Event-free values only.

### 5. [Rule 2 — added, not in the plan's test list] `events::tests::a_future_event_moves_every_predict_path`

D-30 requires the block to be wired through the predict paths, and none of the plan's named tests
would notice a block that trains correctly and is then never added on prediction — the recovery
bar reads weights, not forecasts. The test derives its horizon so it reaches a real planted
occurrence (a fixed 40-day horizon missed one, and the test caught its own vacuity via the
`hit > 0` guard).

### 6. [recorded] `TrainLog` carries the trained block, and `event_weights()` is a method

The plan said "record the event weights and the event-column count in `TrainLog`". The block
itself must travel to the predict paths, and putting it in the log keeps `train`'s return arity
unchanged — so every existing call site stays mechanical. `event_weights()` reads from the block
rather than duplicating it into a field, so there is exactly one source for the number the
recovery and determinism tests assert on.
