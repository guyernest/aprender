<enumeration_filter_decision>
**The flag.** D-34's constant name `fit_np_event_cost_per_column` does not match the
`fit_max_*` / `chronos_max_*` filter in `every_cost_ceiling_constant_is_named_by_an_axis`
(`crates/aprender-forecast/src/types.rs`), so it is not auto-required to have a cost axis
naming it. Is that correct, or a hole in the enumeration?

**Decision: BOTH — the filter is correct for ceilings, AND there is a real second hole beside
it. Do not widen the ceiling filter; add a sibling enumeration.**

1. **The filter is correct, and widening it would be a defect.** That test's contract is
   "every cost CEILING declared in `constants:` must be named by at least one cost axis". A
   ceiling is a value a request is REFUSED for exceeding.
   `fit_np_event_cost_per_column` is a COEFFICIENT: it is multiplied into the priced quantity
   which is THEN compared against `fit_max_np_train_cost`. Nothing is ever refused for
   exceeding it. Capturing it under the ceiling filter would make the test assert that a
   coefficient is a bound, and would require inventing an axis whose `bound:` is a number no
   door check compares against — a dangling claim in the direction the companion test
   `every_cost_axis_names_a_real_bound` exists to refuse.

2. **The hole is real, and it is a different hole.** The enumeration's PURPOSE is that a new
   number in the pricing path cannot be added without something reasoning about it. A
   coefficient added to `constants:` with nothing naming it is exactly that failure, one
   category over. So Task 2 adds a SIBLING test,
   `every_cost_coefficient_constant_is_named_by_an_axis_formula`, deriving its list from
   `constants:` keys containing `_cost_per_` and asserting each such key's name appears
   verbatim in some `cost_axes` entry's `formula:` string — the coefficient's correct
   obligation, which is to be READ by a priced formula rather than to bound anything.

3. **What stays open, recorded rather than claimed closed.** The complete closure is the
   general form: every key in `constants:` falls into exactly one named category (ceiling,
   coefficient, deployment default, warning threshold) and each category carries its own
   obligation. That would immediately require categorising `pool_default`,
   `poisson_normal_branch_lambda`, `chronos_native_horizon`, `fit_min_points` and the two
   regressor warning thresholds plan 06.1-03 adds. It is not built here. Task 2 records it as
   a named follow-up in the contract comment beside the new test, so the narrow enumeration
   is not mistaken for full coverage.
</enumeration_filter_decision>
