  <action>
Add part A to `invariance.rs` as `part_a_every_case_is_deterministic_through_the_door`.

For each of the eight recorded cases, call `forecast::forecast` twice and compare the two
signatures. Assert the number of cases exercised is exactly 8 and carry that count in the
assertion message: a determinism table that silently shrank would otherwise report green while
proving less. This is the same non-vacuity discipline the poisson sweep uses when it pins the
count of checked lambdas.

On a mismatch the message must be diagnostic rather than a bare inequality. Recompute both
signatures with `diagnostics.lbfgs.budget_hit` masked to a fixed value and report whether that
alone accounts for the difference. `budget_hit` is wall-clock dependent — it records whether
the cooperative round-boundary budget in `fit::fit_prophet` was hit — and on a loaded machine
it could flip and read as a signature change. The spike observed it stable across its runs and
flagged the risk anyway. Do NOT remove it from the signature: SC2 puts `diagnostics` inside
the comparison, and carving one key out weakens the gate for the sake of a failure mode that
has never been observed. Making the message name it is what turns a confusing red into an
environment result an operator can act on. State that reasoning in the message itself.

Add `the_signature_ignores_the_two_wall_clock_fields`: take one response, clone it, replace
`fit_seconds` and `predict_seconds` with different finite values, and assert the signature is
UNCHANGED. Without this, "we excluded the timings" is a claim about the code rather than a
property of the function — and a signature containing wall-clock is vacuous in the opposite
direction: always red, which is as useless as always green.

Keep the whole of part A inside `cargo test --lib` reach. Do not mark it `#[ignore]`: the
finding CONTEXT.md records is that the one harness watching an axis could only be reached with
an explicit flag.
  </action>

1. The first `yhat` value stepped by exactly one unit in the last place. Use
   `f64::next_up`-equivalent arithmetic on the bit pattern rather than adding a chosen

a probe that could not get back is testing the wrong thing.

same non-vacuity reason part A pins its case count.

carries `-0.0` where the other carries `+0.0`, in `yhat` and again in `trend`, and assert the
signatures are EQUAL. That is the one deliberate insensitivity in the hasher and it should be
a property rather than a comment; every other bit pattern is significant.

Write the module rustdoc for part B in the terms SC2 uses: a green invariance table with no
falsification probe beside it is indistinguishable from a broken harness, and part B is what
makes the difference observable.
