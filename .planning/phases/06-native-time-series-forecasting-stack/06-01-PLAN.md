The real generalisation in this phase is structural: the request/response shape goes from ONE
server (spike 004) to a family of thin servers that a client switches between by endpoint (D-03),
and CLAUDE.md's Realizar-first table goes from one exception row (SetFit) to a class of
exceptions (Forecasting, plan 06-09).

- Primary noun: the JSON `forecast` tool contract (ds, y, horizon, freq in; ds, yhat, yhat_lower,
  yhat_upper, predict_seconds, diagnostics out) — the spike-004 shape.
- Decision: **promote** the shape to a contract (`contracts/forecast-tool-boundary-v1.yaml`,
  plan 06-06) that BOTH servers are tested against; the Rust argument types stay
  **add-alongside** (`types::ForecastArgs` for the fit server, `chronos::ChronosArgs` with
  nullable `y` and `allow_long_horizon`) because the field TYPES genuinely differ and a single
  struct would force the fit server to accept nulls it cannot fit. Accepted debt: two structs.
  What would force a later promote: a third server whose args differ in more than the three
  fields the Chronos variant differs in today.
- Invariant test (companion, plan 06-07 Task 2): `shared_forecast_shape_holds_for_every_server`
  asserts both advertised schemas require exactly `ds`, `y`, `horizon`, both accept `freq`, and
  both serialized responses carry `model, freq, n_history, predict_seconds, ds, yhat,
  yhat_lower, yhat_upper, diagnostics`. It goes red the instant a server reintroduces a
  private shape.
