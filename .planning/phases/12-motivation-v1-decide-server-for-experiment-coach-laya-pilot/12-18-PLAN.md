eight posts, so for real posts (median 45 tokens, 95th percentile 77) a call admits 5 or 4, and a request of eight realistic posts is
refused at the token budget (the 12-ACCEPTANCE-REPLAY record shows that refusal). The contract field `served_max_texts: 8`, the test
`every_served_task_fits_its_door` (true only for empty posts) and the lambda README sentence all presented 8 as the usable door, and
`prepare_motivation.py` froze `800 / 8` as the literal 100. The hand-off already discloses the effective door, so this is a contract and
documentation overstatement, not a hidden surprise. The same arithmetic holds for the antisemitism row (P 86 leaves 112 tokens for eight
posts; its own record says 5 and 4), so the fix is made for the CLASS, both rows.

Output: contract decide-tool-boundary-v1 v10.2.0, a non-vacuous derived-count test, an honest README and a budget-derived door_b, with the
no-behaviour-change proof recorded and the WR-06 disposition row updated.
