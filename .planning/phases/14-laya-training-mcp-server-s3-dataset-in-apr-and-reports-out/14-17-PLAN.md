Design choices (Claude's discretion, recorded): stage_error never decides the class when an outcome parsed; for pass or gate_fail with a stage error the
records decide (a Train job that exits 1 only because an upload failed leaves complete records, and the same records arrive without a stage error through
the event and reconcile paths, so the class must not depend on the path). The listed-but-absent fix prunes at read time rather than only at tag time
because the same entries feed manifest.json, the presigned links train_status mints and laya-fetch, all of which would otherwise point at an absent
object; tag targets being a subset of the listed keys follows from it. Requirement-ID probes: SKIPPED visibly (no phase requirement IDs mapped).
Threat ids continue at T-14-82 in this plan's register (T-14-78..81 are 14-16's).

Visible signal, recorded choice (checker issue 2): a Train job that exits 1 only because an upload failed leaves complete records, so the records-win rule reports
completed or gate_failed, and training-manifest.json is written complete whatever failed to upload (a failed upload is simply unlisted). The finalizer cannot know
WHICH object is missing in that case, but it can say that the job reported a failure and that the records decided; and for the shape it can see (listed but absent) it
can name the object. Both go in StatusPayload.notes. Two alternatives were rejected: carrying the stage error text in a note (infrastructure text; it would make this plan
widen 14-18's sinks) and recording the loss as an accepted limitation with a test (the required property is a signal beyond the log, which a limitation record does not give).
