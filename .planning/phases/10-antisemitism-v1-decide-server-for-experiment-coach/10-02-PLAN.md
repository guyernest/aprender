<objective>
Give the deploy path the acceptance check the requester will run: one call with one or several texts, one
result per text, probabilities that sum to one and index the labels in task order, and the served sha equal
to the pin, plus the typed outcomes a lowered or full door produces (a count refusal at the limit plus one, a
token-budget refusal during step-down). Build it as modes of the existing probe example (one implementation of
the request path), prove it on the loopback fixture and with a pure evaluator, then run it live against the
stance server. Also make `--plan-only` report the Rust-side shortest built row and the compiled door.

Purpose: D-16 makes the acceptance replay a function-and-identity test whose timings are reported, not gated;
the Phase 8 probe checks identity and labels but never asserts per-result shape or sums. The owner's
2026-10-21 note makes a served maximum of one text legitimate (D-15 amended), so the replay range must follow
the constant, and the `tokens_planned == 8 x P` cross-check that plans 10-04, 10-08 and 10-10 inherited is
false (the distributed plan fills each text to its share of the 800-token budget), so the probe must report
the true shortest row. Having the modes ready before the redeploy means plan 10-09's replay is a run, not a
build.

Output: `run_replay` + `ReplayReport` + pure `evaluate_replay`, `run_count_refusal`, `refusal_bound`,
`served_min_row_tokens` in src/probe.rs with tests; `--replay N`, `--replay-over-limit` and the new plan-only
keys in examples/probe.rs; live JSON lines against the stance server kept in the SUMMARY.
